응모 유형이 달라도, 폼 전체를 다시 만들지 않도록

일본 시장 대상 티켓 응모·당첨 관리자 시스템의 프론트엔드를 전담했습니다. 등록 폼에는 20개 이상의 필드가 있었고, 3개 응모 유형과 옵션에 따라 보여줄 필드와 필수 입력 조건이 달라졌습니다.

폼을 React Hook Form 기반의 7개 섹션으로 나누었습니다. 공통 섹션과 유형별 고유 섹션을 조합하고, 등록·수정 화면에서도 같은 섹션 컴포넌트를 사용하도록 했습니다.

요구사항이 바뀌었을 때 해당 섹션과 검증 규칙을 중심으로 수정하도록 영향 범위를 좁혔습니다.

기존 JSP를 유지하면서 신규 화면은 React로

기존 Admin은 JSP 기반이었고, 신규 기능을 위해 서버 구조 전체를 바꾸기는 어려웠습니다. 기존 팝업의 동작을 유지하면서 React 화면을 추가해야 했습니다.

JSP는 앱을 담는 컨테이너로 두고 React가 신규 화면의 라우팅과 렌더링을 담당하도록 구성했습니다. React 앱은 IIFE 번들로 배포하고, URL 패턴에 따라 팝업과 일반 화면의 마운트 지점을 구분했습니다.

DOMContentLoaded 기반으로 초기화하고, 렌더링 전 콘텐츠를 숨기는 처리를 적용해 초기 화면이 깜빡이지 않도록 했습니다.

기존 JSP 팝업을 유지하면서 신규 기능을 React 화면으로 개발·배포할 수 있는 기반을 마련했습니다.

렌더링 시점이 달라도 같은 방식으로 번역 적용

글로벌 서비스에는 한국어·영어·일본어·중국어가 필요했습니다. JSP와 AngularJS, React가 함께 있는 환경에서 리소스가 분산되어 번역 누락과 중복 구현이 발생했습니다.

JSP와 AngularJS에서 동적으로 생기는 DOM은 MutationObserver로 감지했습니다. HTML의 data-i18n 속성을 이용한 텍스트 처리와 JavaScript 알림·검증 메시지를 공통 i18n 유틸로 통합했습니다.

번역 리소스를 읽기 전에 원문이 먼저 보이지 않도록 i18n-cloak 속성도 정의했습니다. AngularJS의 ng-cloak 개념을 참고해 번역을 적용할 때까지 콘텐츠를 숨겼습니다.

기존 화면과 신규 화면을 함께 유지하면서, 렌더링 시점이 달라도 일관된 다국어 적용 방식을 사용할 수 있도록 했습니다.
